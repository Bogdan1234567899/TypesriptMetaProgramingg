# Task 3 — Deployment Validation

## Що було не так

Список `required` містив 4 обов'язкові переходи, словник `transitions` — тільки 2. Без статичної перевірки систему скомпілювали би і вона впала би в рантаймі під час реального деплою (Testing + Deploy повернув би null/default).

## Вивід валідатора

**Before (неповна таблиця):**
```
Errors: 2
  [ERROR] Missing transition: Testing + Deploy
  [ERROR] Missing transition: Deploying + Done
```

**After (дописано переходи):**
```
Validation OK — Errors: 0
```

## Як працює валідатор

Простий цикл: для кожної пари `(state, event)` зі списку обов'язкових — перевірка `ContainsKey` у словнику переходів. Будь-яка відсутня пара → запис в `errors`. У кінці — або `Errors: 0`, або список конкретних проблем з іменами стану і події.

## Критерій готовності

Валідатор завжди виявляє неповноту таблиці до запуску FSM. Перевірив на двох випадках:
- Неповна таблиця (Before) → Errors: 2 з конкретними іменами.
- Повна таблиця (After) → Errors: 0.

Якщо хтось у майбутньому додасть новий обов'язковий перехід у `required`, але забуде у `transitions` — валідатор одразу це покаже. Це fail-early на рівні даних.
